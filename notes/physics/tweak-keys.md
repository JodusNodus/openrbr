# NTweak key tables in the 1.02 exe

Names for the physics data classes (CDef / CState / CSetup / CSetupOptions), read from the
key tables in `RichardBurnsRally_SSE.exe`. The tables are generated by
`scripts/tweak-keys.py` in the rbr-recomp repository (its member names come from the C++
headers); the findings below are hand-written from them.

Regenerate (in rbr-recomp): `python3 -I scripts/tweak-keys.py --md > /tmp/tweak-keys.md`
(about 20 s; `--no-usage` skips the source grep). The generated tables start at
"Generated tables" and must be refreshed by hand if the script output changes.

Confidence: `high` for owner and key names (exe strings, vtable RTTI, the registration
call), `inferred` for types that come from the ctor walk. Values are the `+0xc` word of a
CReal / CUnsigned and the `+0x10` word of a CVector / CVector4 (`src/rbr/RBR_E48_NTweak.h`,
ctor asm `0x52fea0`, `0x52fec0`, `0x52ff80`). The offsets are the same in the asm and in
the header comments.

## Method

1. **Registration.** Each table is registered by a static-init call
   `push size; push table; mov ecx, DICT; call REG`. `size` is the table length in bytes
   (records = size / 16). All 52 sites were found this way and every record run in
   `.data`/`.rdata` is covered by one of them.
2. **Owner.** `DICT` is returned by `mov eax, DICT; ret` accessors. These sit in vtable
   slots 7 and 8 (`Unk1C` / `Unk20`) of the owning class, so the MSVC RTTI of that vtable
   names the class. Where more than one class shares the accessor, the owner is the common
   base; if there is none, the owner is reported as ambiguous.
3. **Companion.** A dict with no accessor that is passed as `p4` to another registration
   takes that registration's owner. Its offsets are in another object, so its types are
   left unknown.
4. **Types.** The owner ctor writes its vtable, then `lea ecx, [this+off]; call X`. `X` writes
   an NTweak vtable, whose RTTI name gives the type. Array fields
   (`push elem; push count; push size; lea eax, [this+off]; push eax`) take the element
   ctor's type. Loop-built fields are not seen and stay `?`.
5. **Base dict.** Each registration also passes a base dict (`p3`). For `CWheel::CDef`,
   `CCar::CDef` and `CMountedRigidBody`/`CHingedRigidBody` CDef it is the `CSolid::CDef`
   dict, so those objects also carry the `CSolid::CDef` keys (InverseMass at +0x160, value
   +0x16c). The generated tables print the base for each class.
6. **Our name.** The `m_*` member at that offset in the owner class (header parse of
   `src/rbr/*.h`). `generic` = our name only encodes the offset (`m_r160`, `m_unk1C`), so it
   carries no meaning. `uses` = `src/rbr/*.cpp` lines that name the member (across all
   classes, so an upper bound).
7. **LSP check.** `LSP block kinds` = the `("Kind" ("NAME" ...))` blocks in the retail
   `physics.rbz` / `misc.rbz` where the key word occurs. `absent` = the word occurs in no
   retail `.lsp` (state keys are in `misc.rbz`).

## Summary

- 52 tables, 22 classes (including the setup and season classes), 50 with an owner.
- 379 of 1104 records have a type. The rest are loop-built setup and gear fields, and
  `CMaterialManager`'s array (see Open items).
- `0x7ca678` is ambiguous (two classes share its accessor). `0x7c6df0` has no owner.
- CFlags names: `0x7cbc10` is a pointer array of 18 names (`FACE_COLL` ... `INTERNAL`),
  indexed by bit. It is not a record table, so it is only listed at the end of the output.
- The `CSolid::CDef` (10 keys) and `CSolid::CState` (6 keys) names match
  `notes/physics/rigid-body.md` section 2a exactly (offsets, value offsets, types).

## Findings

### Contradictions (name or usage vs key)

1. **`CCar::CDef+0x22c` and `+0x23c` are not downforce gains (resolved).** The key table
   (`0x7c6578`) names `+0x220` `MaxSteeringLock` (CReal, value `+0x22c`) and `+0x230`
   `SteeringRackRatio` (CReal, value `+0x23c`). `notes/physics/car-body.md` section 2b calls
   these "downforce gain A/B". Our code multiplies them into the downforce target at
   `src/rbr/RBR_E35_Car.cpp:210-213` (`f1 = def+0x23c; f2 = def+0x22c;
   p+0xb0c = f1*f2*p+0xafc`). Either the original multiplies steering values into downforce
   (then the name is wrong), or the asm reads a different field there (then the C++ offset
   is wrong). Route: car-body owner; check the asm of the function holding `E35_Car.cpp:210-213`.
   Update (BC1, 2026-10-14): `CCar::UpdateFfbTorque` (0x4e7ff0) also reads def+0x23c --
   asm `0x4e805f: movss 0x23c(%eax)` with eax=[ecx+0x34] (def), and no +0x22c read
   anywhere in 0x4e7ff0-0x4e80a3. Our C++ (`RBR_E34_CarC.cpp`, def+0x23c) matches the
   asm. Verified identical 12,084 steps with that offset.
   Resolved (`notes/ngp-ffb.md`, 2026-10-16): the key names are right and the old reading was
   wrong. The chain is steering force feedback: `+0xb0c` is the rack position
   (`MaxSteeringLock * SteeringRackRatio * slewed input`) and `+0xaec` the filtered steering
   torque that the FFB emitters read through `FfbNorm` (`/ MaxFFTorque`). The code is renamed.
2. **`CSolid::CState` `Progress` is at `CSolid+0x170`, not `+0x110` (MEDIUM).**
   `rigid-body.md` section 2c and open question 1 say `+0x110`. With the state object at
   `CSolid+0xe0` and the key at state `+0x90`, the object is at `+0x170` and the value at
   `+0x17c`. Correct both places. This does not change the `VfDx`/`VfEx` finding
   (`+0x290` is still the progress they read).
3. **`CWheel::CDef+0x41c` `strut_static_offset` has no key (MEDIUM).** `wheel.md` (line 90)
   names def `+0x41c` (value of a CReal at `+0x410`). The table has no key at `+0x410`.
   The nearest key is `DriveAxleMountOffset` (CReal at `+0x420`, value `+0x42c`). Either
   the name belongs to `DriveAxleMountOffset` (then the offset is `+0x42c`) or the field
   at `+0x410` is unnamed. Check the asm that reads `def+0x41c` before naming it.
4. **`CCar::CDef+0x16c` `inverse_mass` is consistent, through the base dict (no change).**
   The `CCar::CDef` table itself has no InverseMass; the key is inherited from the
   `CSolid::CDef` base dict (InverseMass at `+0x160`, value `+0x16c`). `CarC.cpp:56`
   (`s = -1/def+0x16c`) therefore divides the InverseMass key, which gives `-mass` as
   `car-body.md` open 3 says. The key confirms the stored value is the inverse mass, so the
   open question is only whether the gust term should use mass, not the name.
5. **`CDrive::CDef+0x620` is `MaxFootbrakePressure` (name confirmed, no change to the
   code).** `engine-driveline.md` (the `0x620` row) calls it `brake_max_front?`. The key is
   `MaxFootbrakePressure` at `+0x614` (value `+0x620`). The name is not in any retail
   `.lsp` (see Names not in the LSP). Rename the note's field to `max_footbrake_pressure`.
6. **Diff torque names confirmed.** `engine-driveline.md` `0x58 + a*0x60 diff_max_torque`
   matches the keys `CenterDiffMaxTorque` (`+0x4c`), `FrontDiffMaxTorque` (`+0xac`) and
   `RearDiffMaxTorque` (`+0x10c`), so `a = 0, 1, 2` is centre, front, rear. The types are not
   recovered (the note says f32 at `+0xc`).
7. **`CDrive::CState+0x540` is `Gear`, and the note's `+0x54c` gear value is consistent.**
   The type is not recovered, so the `i32` in the note is unchecked by the table.
8. **`CSpringDamper` names agree with the note, with one unkeyed slot.** The CSetup keys
   (`BumpHighSpeedBreak`, `DampingBumpHighSpeed`, `HelperSpringMinLength`) match
   `spring-damper.md` section 2b. The CDef-side keys have other names
   (`HighSpeedBreakBump` `+0xdc`, `HighSpeedDampingBump` `+0xfc`), which is a mapping, not a
   contradiction. The CDef has no key at `+0x5c` (`helper_min_length`), so the setup's
   `HelperSpringMinLength` copies into an unnamed CDef field.
9. **`vcu.md` is consistent with the key table.** `Gear{k}Upshift`/`Downshift` at
   `0x0c + 0x20k`, `RPMLimit` (`0x17c`), `CenterDiffHandbrakeRelease` (`0x18c`) and
   `LeftFootBrakeThreshold` (`0x19c`) match. `0x14c`, `0x15c` and `0x16c` have no key, so
   "name none" in `vcu.md` stands.
10. **Spelling of `DebugID`.** `CSpringDamper::CDef` and `CPassenger::CDef` use
    `DebugID`; `CWheel::CDef` uses `DebugId`, which is the only spelling in any retail
    `.lsp`. The spring-damper `DebugID` is therefore not settable from the LSP files.

### Names not in any retail .lsp (exe-only keys)

These keys are read by the exe but never set by a retail `.lsp` or `misc.rbz`. Their
meaning is therefore from code only:

- `CSolid::CDef`: `bSpecial`, `AngularThresholdVelocity`, `LinearThresholdVelocity`.
- `CSpringDamper::CDef`: `DebugID`, `DroopStiffness`, `HighSpeedBreakBump`,
  `HighSpeedBreakRebound`, `HighSpeedDampingBump`, `HighSpeedDampingRebound`.
- `CDrive::CDef`: `MaxFootbrakePressure`, `BrakeRatio_LF`/`RF`/`LR`/`RR`.
- `CHingedRigidBody::CDef`: `HingeRestitution`, `SpringRate`, `Damping`, `Spring1*`.
- `CVehicleControlUnit::CDef`: `Gear8Upshift`, `Gear8Downshift`, `Gear9Upshift`,
  `Gear9Downshift`.
- `CPhysics::CDef`: `MaxExpirableCount`, `DamageZone`, `SingleStepperDelay`.
- `CTyre::CState`: `CarcassStiffness`. `CCar::CState`: `vecLocalLinearAcceleration`,
  `vecLocalAngularAcceleration` (runtime state).
- Runtime state, absent by design: `CSolid::CState` `Progress`, `IsActive`, `WipedOut`;
  `CPhysics::CState` `ObjIdQueue`; `CSpringDamper::CState` `LastDeflection`.

## Open items

- **Types not recovered (725 of 1104).** Most are setup objects built by loops:
  `CDrive::CSetupOptions` (227), `CMaterialManager` (134, all array), `CTyreTypes` (56),
  `CVehicleControlUnit::CSetup` (110), `CDrive::CSetup` (10), and the `CSetupOptions` of
  most classes. Also loop-built gear fields in `CVehicleControlUnit::CDef` (20 of 23).
  Fix: walk the loop bodies, or read the `.lsp` value shapes (not done here: values such as
  `15000000` look like ints but are floats).
- **`0x7ca678` ambiguous.** `CCarLightSystem::CState` and `CEngine::CState` both return dict
  `0x165919c`. The keys `InletPressure` and `ExhaustPressure` are engine keys, so
  `CEngine::CState` is the likely owner. Confirm from the asm of the `CEngine::CState`
  accessor before assigning it.
- **`0x7c6df0` unowned.** One record, `Dummy` (CBase, `+0x10`). Dict `0x8ef7c8` has no
  accessor and no companion link. Probably a placeholder. Not used by any physics code
  checked.
- **`Dummy` placeholders.** Several classes carry a `Dummy` record (`CVehicleControlUnit::CState`
  `+0x0c`, `CEngine::CSetup` `+0x0c`, the `CHingedRigidBody` companion `+0x04`). Treat them
  as placeholders, not fields.
- **Our names.** Most of the physics members are generic (`m_r160`, `m_unk1C`). The `ours`
  column is `no member` where the header parse found nothing (the `CDrive`, `CWheel`,
  `CEngine`, `CTyre` CDef classes are declared across several headers). Naming them from
  the table is the next step; the 'generic' rows are the list to rename.
- **Not checked here:** `tyre.md` (CScratch offsets are not in the key tables), `collision.md`,
  `damage.md`.
- **Base dict chains:** `CWheel::CDef`, `CCar::CDef`, `CHingedRigidBody::CDef`,
  `CMountedRigidBody::CDef` take `CSolid::CDef` as base; `CCar::CState` takes
  `CSolid::CState`. The key lookup falls back to the base dict. If the layout does not match
  the RTTI base (`CCar::CDef` is `E43EntityDef`-based in our headers), check the `+0x160`
  InverseMass offset in the car def first.
